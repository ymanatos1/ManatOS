# ManatOS Express Platform

**Status:** Under Development / Under Testing

A modern Express 5 + TypeScript baseline with independently runnable **API** and **Express/EJS UI** projects, common metadata contracts, in-memory/JSON persistence, registration/sign-in, sessions, Swagger, Postman and automated-test scaffolding.

## Quick start

Requires Node.js **24.19.0 LTS** (`.nvmrc`).

Windows PowerShell:

```powershell
.\scripts\init-all.ps1
npm run dev
```

Or manually:

```bash
cp api/.env.example api/.env
cp ui/.env.example ui/.env
npm install
npm run build
npm run dev
```

Open:

- UI: `http://localhost:3001/`
- Swagger: `http://localhost:3000/api/`
- OpenAPI JSON: `http://localhost:3000/api/openapi.json`

The bootstrap administrator is configured in `api/.env`. Change the example password before using the project outside local development.

## Business objects

The four current first-class SysBOs are:

- **SysUser** (`sys-users`) — website/security account.
- **SysPrincipal** (`sys-principals`) — customer/commercial identity.
- **SysApplication** (`sys-applications`) — managed/licensed application.
- **SysLicense** (`sys-licenses`) — customer license for an application.

Supporting entities are `SysExternalIdentity`, `SysUserPrincipal`, and a `SysUserInvitation` scaffold for customer-first onboarding.

### Identity separation

A `SysUser` is created when somebody registers on the website. Registration starts with role **Guest**. A `SysPrincipal` is created/linked only when a customer identity exists. Linking a normal Guest to a customer principal promotes the website role to **User**. **Admin** remains a privileged website role.

## Metadata and data are separate

Every BO has hard-coded **BO metadata** identified by a stable string such as `sys-principals`. Field metadata is a keyed object whose keys are canonical field/property names.

Actual data is separate. Every entry has an immutable storage-generated GUID in `id`. The in-memory store and JSON persistence key records by this GUID.

The website adds a second category, **UI metadata**, containing:

- `ListViewModel`
- `EditViewModel`
- `GridConfiguration`
- `FilterDefinition`
- `PaginationConfiguration`
- icons and UI actions

A future mobile application can reuse BO metadata while defining different UI metadata.

API metadata is explicit:

```text
GET /api/v1/SysUsers/$metadata
GET /api/v1/SysPrincipals/$metadata
GET /api/v1/SysApplications/$metadata
GET /api/v1/SysLicenses/$metadata
```

Normal list calls return data/paging. `includeMetadata=true` adds BO metadata when convenient.

## Data rules

- Every BO `name` is user-provided and unique (case-insensitive in the current adapter).
- `SysUser.email` is also unique.
- `SysApplication.appName` is also unique.
- Duplicate unique values produce `409 Conflict`; the UI preserves the edit form and displays the application-error popup.
- IDs are GUIDs generated by the storage provider (`crypto.randomUUID()` for memory; a future database can generate them itself).

## Registration and sign-in

The website registration popup can offer:

- Google (when configured)
- Facebook (when configured)
- Email

Email registration asks for unique user-name, unique email and password.

External registration first authenticates the provider, checks email uniqueness, then shows the provider email read-only and asks for a **unique user-name** and an **optional local password**.

Passwords require:

- more than 8 characters (minimum 9)
- at least one alphabetic character
- at least one number
- at least one symbol

Passwords are Argon2id hashes. API/UI projections expose `hasPassword`, never the hash.

Local sign-in accepts **email or user-name + password**. Google/Facebook sign-in never asks for a local password. An externally registered user can later set one.

The combined welcome/verification email and password reset/change emails currently use a console email adapter. Real SMTP can be added behind `IEmailService`.

The **Forgot or set password** flow uses one-time hashed transient tokens and deliberately returns a generic public response to avoid account enumeration.

## Sessions

Sessions are **never** persisted to `data/database.json`.

Their rolling idle timeout is configured in minutes:

```text
SESSION_IDLE_TIMEOUT_MINUTES=30
```

The baseline uses Express MemoryStore for development/single-process use only. A production multi-instance deployment should replace it with Redis or another dedicated session store.

## UI

The supplied ManatOS logo/favicon are included.

The responsive shell provides:

- navy top bar with clickable company logo;
- version at the right;
- sign-in/sign-up icons or logged-user profile menu;
- Account details, Personal details and Logout menu items;
- metadata-driven nested horizontal navigation;
- authenticated-only nested vertical navigation;
- central workspace;
- optional right details panel;
- corporate footer.

Generic SysBO CRUD pages provide:

- Bootstrap/EJS grid;
- metadata-defined field order;
- sorting;
- multiple field filters;
- fully configurable pagination;
- green **Add new**;
- edit by clicking the primary/name field;
- red **Delete entry** + confirmation popup;
- unsaved-changes **Cancel / Discard / Save** popup;

Every page receives the complete read-only application context through `res.locals.app`:

```text

├── version
├── scopes

│   ├── user
│   ├── request
│   └── workspace
│       └── application (when playing a SysApplication)
├── sysBO
└── navigation
```

## Error handling and semantic operation traces

HTTP/navigation errors use `http-errors` and EJS error pages.

Application errors use typed `AppError` plus a nested `AsyncLocalStorage` semantic operation trace. Successful nested detail is pruned; completed siblings remain summaries; a failed branch remains fully expanded down to the failed operation.

Selected context values may be attached to operations. Sensitive names (`password`, `token`, `secret`, `cookie`, `session`, API key, etc.) are automatically represented as:

```text
********
```

The same canonical error can be projected to API JSON, the UI error popup and a bounded session error log. API error detail is configurable (`none`, `basic`, `operations`, `full`).

## Storage

Current implementation:

```text
Services
  -> InMemoryDataStore / generic repositories
  -> JsonFilePersistence
  -> data/database.json
```

JSON writes use temporary-file + rename. In-memory transactions snapshot the Maps and roll back on failure. Future SQL/database adapters can replace this implementation without changing services or presentation layers.

## Current limitations

This is a baseline rather than a completed production system. In particular:

- API bearer-token/third-party-client authorization is intentionally not implemented yet.
- UI sessions and verification/reset tokens are memory-only.
- Real SMTP is not configured.
- Google/Facebook require real provider credentials/callback URLs.
- UI integration tests are scaffolded; broaden them as pages stabilize.
- SysApplication playground internals are intentionally deferred.
